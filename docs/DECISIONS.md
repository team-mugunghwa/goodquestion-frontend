## 001. 상태관리로 Provider 사용

- **2026-08-08 / 승인됨**
- **맥락**: Flutter 상태관리 선택지가 많고, 팀원마다 익숙한 게 다름.
- **결정**: `provider` + `ChangeNotifier` 기반 MVVM.
- **이유**: 러닝커브가 가장 낮고 Flutter 공식 문서/한국어 자료가 가장 많음. 팀 프로젝트 기간 안에 전원이 같은 수준으로 쓸 수 있는 게 중요.
- **대안**: Riverpod(컴파일 타임 안전성은 좋지만 개념이 하나 더 늘어남), BLoC(보일러플레이트 과다), GetX(구조를 망가뜨리기 쉬워 클린 아키텍처와 상충).
- **결과**: `context.watch` / `context.read` 사용처를 규칙으로 강제해야 함. 전역 Provider 남용 시 상태 누수 위험 → 화면 단위 Provider를 기본으로 함.

## 002. Feature-first 폴더 구조

- **2026-08-08 / 승인됨**
- **맥락**: 클린 아키텍처의 3레이어를 어떻게 배치할지.
- **결정**: `features/<기능>/{data,domain,presentation}`. 레이어를 최상위에 두지 않음.
- **이유**: 기능 하나를 작업할 때 폴더 한 곳만 열면 됨. 4명이 서로 다른 feature를 맡으면 **git 충돌이 거의 안 남**.
- **대안**: layer-first (`lib/data/`, `lib/domain/`, ...) — 레이어가 한눈에 보이지만 작업 동선이 나쁘고 충돌이 잦음.
- **결과**: 공통 코드가 어디 속하는지 애매할 때가 있음 → `core/`에 두고, 두 개 이상의 feature가 쓰면 `core/`로 승격하는 규칙.

## 003. DI는 get_it + provider 역할 분리

- **2026-08-08 / 승인됨**
- **맥락**: Repository/UseCase까지 Provider로 주입하면 `BuildContext`가 domain·data 레이어까지 새어 들어옴.
- **결정**: 위젯 트리와 무관한 객체(Repository, UseCase, DataSource, DioClient)는 **get_it**, 화면 생명주기를 따르는 ViewModel은 **provider**.
- **이유**: ViewModel이 `BuildContext` 없이도 테스트 가능해짐. `dispose` 타이밍은 provider가 알아서 관리.
- **대안**: provider만 사용 — 의존성이 위젯 트리에 묶여 단위 테스트가 어려워짐.
- **결과**: 등록 위치가 두 군데가 됨 → `core/di/injector.dart` 한 파일로 모으고, 새 의존성은 반드시 거기 등록.

## 004. DTO와 Entity 분리

- **2026-08-08 / 승인됨**
- **맥락**: 서버 JSON을 그대로 화면까지 들고 가면 편하지만, 서버 스펙이 바뀔 때 화면 코드가 전부 깨짐.
- **결정**: `data/dtos/XxxDto` (fromJson 보유) → `toEntity()` → `domain/entities/Xxx` (순수 Dart).
- **이유**: 서버 필드명이 바뀌어도 `toEntity()` 한 곳만 수정. 백엔드가 아직 스펙을 확정 못 한 상태에서 특히 유효.
- **대안**: Entity에 `fromJson` 직접 부착 — 코드는 줄지만 domain이 서버 스펙에 종속됨.
- **결과**: 변환 코드가 늘어남 → DTO의 `fromJson`은 `json_serializable`로 자동 생성해 보일러플레이트를 줄임. Entity는 순수 Dart 클래스로 손으로 씀.

## 007. pubspec.lock 커밋함

- **2026-08-08 / 승인됨**
- **맥락**: 기존 `.gitignore`(Dart 라이브러리 템플릿)가 `pubspec.lock`을 제외하고 있었음.
- **결정**: **커밋한다.** `.gitignore`에서 제거함.
- **이유**: 앱 프로젝트는 팀 전원과 CI가 **동일한 패키지 버전**을 써야 함. lock을 무시하면 사람마다 다른 버전이 깔려 재현 불가능한 버그가 생김. (라이브러리 프로젝트일 때만 lock을 제외하는 게 맞음)
- **결과**: 패키지 추가 시 lock 충돌 가능 → 손으로 고치지 말고 삭제 후 `flutter pub get` 재생성.

## 010. main 브랜치 보호 없이 운영

- **2026-08-09 / 승인됨**
- **맥락**: "직접 push는 되게 하고, CI 통과만 필수로 걸자"는 요구가 있었음.
- **조사 결과 — 둘 다 불가능했음**:
  1. `team-mugunghwa` 조직이 **Free 플랜**이고 저장소가 **private** → 브랜치 보호·룰셋 API가 `403 Upgrade to GitHub Pro`. 애초에 규칙을 걸 수 없음.
  2. 설령 유료로 올려도 **"직접 push 허용 + CI 통과 필수"는 GitHub에서 공존하지 않음.** 필수 상태 체크는 *머지 시점*에 검사하는 규칙이라 이미 올라간 push에는 적용될 시점이 없고, 실제로 켜면 직접 push가 `required status check is expected`로 거부됨.
- **결정**: 보호 규칙을 걸지 않는다. CI는 매 push마다 돌지만 **강제하지 않고 팀 약속으로 지킨다.**
- **대안**: 저장소를 public 전환(보호·Actions 무료) — 코드 전면 공개가 부담. GitHub Team 유료 전환 — 학교 팀 프로젝트에 과함.
- **결과**: 깨진 `main`이 올라갈 수 있음. 그래서 [CONVENTIONS.md](CONVENTIONS.md#3-main에-올리기)에 **push 전 로컬 검증 + push 후 Actions 초록불 확인**을 명시적 약속으로 넣음. 팀이 커지거나 사고가 반복되면 재검토.

## 011. web 플랫폼을 "개발 미리보기용"으로만 추가

- **2026-08-09 / 승인됨**
- **맥락**: 배포 타겟은 Android/iOS인데, Windows 개발 PC에 Android SDK가 없으면 **앱을 띄워볼 방법이 하나도 없음** (iOS는 Mac 필요). 태블릿 우선 UI라 화면을 못 보면 레이아웃 작업이 막힘.
- **결정**: `web` 플랫폼을 추가하되 **배포 대상이 아니라 개발 미리보기 수단**으로만 쓴다. CI에 web 빌드 job을 넣지 않는다.
- **이유**: Android Studio + SDK는 10GB 이상이라 설치 부담이 큼. web은 수십 MB에 `flutter run -d chrome` 한 줄이면 되고, **브라우저 창 크기를 조절해 태블릿/폰 레이아웃을 즉시 비교**할 수 있어 반응형 작업에 오히려 편함.
- **주의**: web에는 `dart:io`가 없다. 이 결정 때문에 `app_config.dart`의 `Platform.isAndroid`를 `defaultTargetPlatform`으로 교체했음. **앞으로도 `dart:io`를 쓰면 web 미리보기가 깨진다.**
- **결과**: 최종 확인은 **반드시 실기기/에뮬레이터**에서. web에서 잘 보인다고 태블릿에서 같다는 보장은 없음(폰트·터치 타겟·SafeArea가 다름).

## 012. 앱 아이콘은 flutter_launcher_icons로 생성

- **2026-08-09 / 승인됨**
- **맥락**: Android/iOS 앱 아이콘은 해상도별로 수십 개 파일이 필요함. 손으로 만들면 로고가 바뀔 때마다 전부 다시 만들어야 함.
- **결정**: `flutter_launcher_icons`(dev 의존성)로 로고 하나에서 전부 생성. 설정은 `pubspec.yaml`에.
- **이유**: 로고 교체 시 `dart run flutter_launcher_icons` 한 줄이면 끝남. 생성된 아이콘은 커밋해서 클론 직후 바로 빌드되게 함.
- **주의 2가지**:
  1. **iOS 아이콘은 투명도를 허용하지 않음.** `remove_alpha_ios: true` + 흰 배경으로 채움. 안 하면 App Store 업로드가 거부됨.
  2. **Android 어댑티브 아이콘은 런처가 모양(원/사각/스퀘어클)을 정하므로 가장자리가 잘림.** 그래서 전경용으로 여백을 더 준 별도 파일(`assets/icons/app_icon_foreground.png`, 마크 높이 290/512)을 씀. `logo_mark.png`(높이 400/512)를 그대로 쓰면 원형 런처에서 Q의 위아래가 잘림.
- **결과**: `android/app/src/main/res/`와 `ios/Runner/Assets.xcassets/`의 아이콘 파일은 **생성물이므로 직접 수정하지 말 것.** 원본 이미지를 고치고 재생성해야 함.

## 013. 라우팅은 go_router, 라우트는 `lib/core/router/`에 모음

- **2026-08-09 / 승인됨**
- **맥락**: 화면이 12개로 정해졌고 `/stories/:storyId`, `/play/:sessionId/recap`처럼 **경로 파라미터와 중첩 경로**가 있음. 보호자 리포트는 나중에 **알림 딥링크**로 바로 진입해야 함. 기존에는 `MaterialApp(home:)` 하나에 `Navigator.push`뿐이라 경로라는 개념 자체가 없었음.
- **결정**: `go_router`를 넣고 `MaterialApp.router`로 바꿈. 라우트 표는 `lib/core/router/app_router.dart`, 경로 문자열은 `app_routes.dart` 상수로만 둔다. **화면 코드에 경로 문자열을 직접 쓰지 않는다.**
- **이유**: 딥링크와 경로 파라미터를 직접 파싱하지 않아도 됨. 나중에 붙일 **게이트(보호자 확인·아이 프로필 미등록 시 이야기 진입 차단)** 를 `redirect` 한 곳에서 처리할 수 있음 — 화면마다 흩뿌리면 빠뜨린 곳이 반드시 생김.
- **대안**: `onGenerateRoute`(패키지 추가 없음)를 고려했으나, 경로 파라미터를 손으로 파싱해야 하고 게이트 리다이렉트를 결국 직접 만들게 됨.
- **주의**: **web은 기본 해시 URL 전략을 그대로 씁니다.** 미리보기 주소는 `http://localhost:PORT/#/stories/12` 형태입니다. 해시를 떼려면(`/stories/12`) 정적 서버에 index.html 폴백 설정이 필요한데, web은 배포 대상이 아니라 그 비용을 지지 않았습니다. → 011
- **결과**: `lib/core/router/`는 여러 명이 동시에 건드리는 파일이 됨. 라우트 추가 시 팀 채널에 알릴 것. → [CONVENTIONS.md](CONVENTIONS.md) 6장

## 014. 디자인 시스템을 화면 작업보다 먼저 확정, 다크 모드는 만들지 않음

- **2026-08-09 / 승인됨**
- **맥락**: 화면 12개를 각자 하나씩 맡아 만들 예정. 토큰이 없으면 **12개 화면이 12가지 디자인**이 됨. 게다가 이 앱은 사용자가 둘(초1~3 아이 / 보호자)이라 "적당히 예쁘게"가 서로 다른 방향을 가리킴.
- **결정**:
  1. 색·타이포·간격·모서리·터치 타겟·그림자·아이콘·모션을 `lib/core/theme/` + `app_icons.dart` 토큰으로 먼저 확정하고, 규칙은 [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md)에 둔다. **화면 코드에서 토큰 밖의 값을 만들지 않는다.**
  2. 화면을 **아이 / 보호자 두 세계**로 나눈다. 바탕은 `AppCanvas.day` / `.night` / `.guardian` 세 가지뿐.
  3. 폰트는 **Pretendard(SIL OFL 1.1) + 나눔스퀘어라운드(무료·상업적 이용·임베딩 허용)** 두 개. 패키지(`google_fonts`)가 아니라 **에셋으로 번들**한다.
  4. 아이콘은 **Flutter 내장 Material 아이콘의 `_rounded` 변형만**. 아이콘 패키지를 추가하지 않는다.
  5. **다크 모드를 만들지 않는다.** `themeMode: ThemeMode.light` 고정, `AppTheme.dark` 삭제.
- **이유**:
  - 나눔스퀘어라운드는 **로고 워드마크와 같은 둥근 획**이라 로고 옆에서 이질감이 없음. 저학년 대상 무료 한글 폰트 중 이 조건을 만족하는 게 드묾.
  - `google_fonts` 패키지는 **런타임에 폰트를 내려받음** → 첫 실행에 글자가 늦게 뜨고, 네트워크 없으면 기본 글꼴로 나옴. 게다가 나눔스퀘어라운드는 Google Fonts에 없음.
  - 아이콘 패키지를 섞으면 굵기와 광학 크기가 어긋남. 내장 `_rounded` 세트로 필요한 아이콘이 전부 있었음.
  - 다크 모드: 장면 이미지·캐릭터 에셋이 밝은 배경 전제로 그려지고, **아이 동선의 절반(완료·행성)은 이미 밤 배경**임. 화면마다 두 벌을 검수할 여력이 없고, 잘못 만들면 파스텔 대비가 무너져 아이가 글자를 못 읽음.
- **대안**:
  - Material 3 `ColorScheme.fromSeed` 만 쓰고 토큰을 따로 안 두기 — 생성 팔레트는 대비가 자동으로 맞지만 **별가루·낮/밤 바탕·아이용 터치 타겟처럼 이 제품 고유의 개념을 표현하지 못함**.
  - 아이/보호자용 `ThemeData` 두 벌 — 라우트마다 테마를 갈아 끼워야 하고, `Theme.of(context)` 결과가 화면마다 달라져 실수하기 쉬움. 대신 **공용 테마 1벌 + 아이 전용 명시적 토큰(`AppTypography.kid*`, `AppSizes.tapChild*`)** 으로 감.
- **결과**:
  - `lib/core/theme/` 가 충돌 잦은 파일 목록에 하나 더 늘어남 → 수정 전 팀 채널 공지. ([CONVENTIONS.md](CONVENTIONS.md#6-충돌이-자주-나는-파일))
  - **폰트 파일을 아직 커밋하지 않았음.** 없어도 앱은 시스템 글꼴로 그냥 도는데, 그래서 "시안이랑 다른데?" 의 원인이 되기 쉬움. 설치 절차는 [`assets/fonts/README.md`](../assets/fonts/README.md).
  - 나중에 다크 모드가 필요해지면 `AppColors` 를 `ThemeExtension` 으로 바꾸는 작업이 한 번 필요함. 지금은 그 비용을 미룸.

## 015. 화면별 더미 JSON을 에셋으로 두고, Mock Repository가 읽음

- **2026-08-09 / 승인됨**
- **맥락**: 백엔드가 아직 없는데 화면 12개를 각자 만들어야 함. 홈만 해도 아이 프로필·진행 중 세션·추천 이야기·별가루 잔액 네 덩어리가 필요하고, **"진행 중 세션 없음", "아이 프로필 없음" 같은 분기를 눈으로 확인**해야 함.
- **결정**: 화면 하나당 더미 파일 하나를 `assets/dummy/<화면>.json`에 두고, `LocalDataSource`가 `rootBundle`로 읽어 DTO → Entity로 올린다. 파일 모양은 서버 응답 `data`와 **1:1**로 맞춘다. (첫 사례: `assets/dummy/home.json` ↔ `GET /home`)
- **이유**:
  - 더미를 Dart `Map` 리터럴로 코드에 박으면 기획이 문구·개수를 바꿀 때마다 코드를 고쳐야 함. **파일이면 코드를 안 건드림.**
  - 파일 모양이 그대로 **백엔드와의 계약 초안**이 됨. `docs/API.md`에 붙일 표를 따로 만들 필요가 없음.
  - DTO를 실제로 통과시키므로 서버가 붙는 날 `LocalDataSource` → `RemoteDataSource` 교체만 하면 됨. 화면·ViewModel 코드는 안 바뀜.
  - 분기 확인은 파일을 잠깐 고쳐서 함 (`"inProgressSession": null`).
- **대안**: `QuestionRepositoryMock`처럼 코드 안에 시드 데이터를 두는 방식. 목록형 화면(항목 12개 생성)에는 그게 낫고, 그 코드는 그대로 둔다. **모양이 복잡하고 분기가 있는 화면**만 파일로 간다.
- **주의**: 더미는 컴파일러가 검사하지 않는다. 필드 이름을 하나 잘못 쓰면 앱을 켜야 안다. 그래서 **더미가 Entity로 파싱되는지 확인하는 테스트를 함께 둔다** (`test/features/home/data/home_dummy_test.dart`).
- **결과**: 서버가 붙으면 `assets/dummy/`와 `*LocalDataSource`는 통째로 지운다. 화면 코드에 흔적이 남지 않는 게 이 구조의 목적이다.

## 016. 오디오 재생기를 아직 넣지 않고, 재생 상태만 시뮬레이션

- **2026-08-09 / 승인됨**
- **맥락**: 이야기 상세의 "들려줘"와 단어장의 스피커는 **음성 우선 원칙의 핵심**이다(글을 못 읽는 아이가 버튼 하나로 내용을 듣는다). 그런데 음성 파일이 아직 하나도 없고, 백엔드 오디오 경로도 미정이다.
- **결정**: `just_audio` 같은 재생 패키지를 넣지 않는다. `core/widgets/speaker_button.dart` 가 **재생 중 상태만 1.8초 시뮬레이션**한다(아이콘이 파형으로 바뀌었다가 돌아옴). 화면·상태 전이는 진짜와 동일하게 만들어 둔다.
- **이유**:
  - 파일도 없는데 패키지부터 넣으면 `pubspec` 에 안 쓰는 의존성이 남고, 플랫폼별 권한·초기화 코드가 따라 들어온다. 되돌리는 비용이 넣는 비용보다 크다.
  - **UX 검증에는 재생 "상태"만 있으면 충분하다.** 아이가 버튼을 눌렀을 때 무언가 반응한다는 것, 재생 중임이 무음 환경에서도 보인다는 것 — 목업에서 확인할 건 그거다.
  - 재생기가 들어올 자리를 위젯 하나로 좁혀 두었으므로, 교체 시 화면 코드는 손대지 않는다.
- **주의**: 시뮬레이션이라는 사실이 코드에만 있으면 나중에 "왜 소리가 안 나지?"로 반나절이 샌다. `SpeakerButton` 의 문서 주석 첫 줄에 명시했고, 여기에도 남긴다.
- **결과**: 음성 파일이 준비되면 `SpeakerButton._toggle` 과 `mockDuration` 만 실제 재생기로 교체한다. 그때 이 결정을 "완료됨"으로 갱신할 것.

## 017. 보호자 확인 게이트는 클라이언트 상태 1회 통과로 두고, 라우터 가드는 미뤘음

- **2026-08-09 / 승인됨**
- **맥락**: 리포트(`/mypage/report*`)는 아이가 혼자 열면 안 된다(PRD F-09). [ARCHITECTURE.md](ARCHITECTURE.md)는 이런 게이트를 `app_router.dart`의 `redirect`에 한 번만 붙이라고 못 박아 두었다. 그런데 게이트 자체(모달 5)는 아직 설계 전이고, 확인 방법(간단한 산수? 생년월일?)이 정해지지 않았다.
- **결정**: 지금은 **마이페이지의 리포트 메뉴 호출 지점에서만** 검사한다. 통과 여부는 `GuardianGate`(getIt 싱글턴)가 메모리로 들고 있고, 같은 세션 안에서 한 번만 묻는다. 로그아웃 시 `reset()`.
- **이유**:
  - 게이트 UI가 없는 상태에서 라우터 `redirect`부터 만들면, 리다이렉트 대상 화면이 없어서 개발 중 딥링크가 전부 막힌다.
  - 목록↔상세를 오갈 때마다 확인을 요구하면 보호자가 못 쓴다. 그래서 "1회 통과 유지"는 게이트 UI와 무관하게 지금 정해도 되는 계약이다.
- **주의**: ⚠️ **지금은 주소창으로 `/mypage/report`에 직접 들어가면 게이트가 걸리지 않는다.** 목업 단계에서는 오히려 편하지만, 모달 5가 확정되면 **반드시 `redirect`로 옮겨야** 한다. 화면마다 검사하는 방식으로 두면 딥링크·알림 진입 경로를 반드시 빠뜨린다.
- **결과**: 옮길 때 손댈 곳은 `app_router.dart`의 `redirect`와 `MyPageView._openReport` 두 군데뿐이다. `GuardianGate`는 그대로 쓴다.

## 018. 실제 OAuth 를 붙이지 않고 로그인 이후의 분기만 목업으로 만듦

- **2026-08-09 / 승인됨**
- **맥락**: `/auth`는 서비스의 유일한 관문이다(F-01). 카카오·구글 로그인 버튼이 있지만, 실제 SDK 연동은 **앱 키 발급 + 플랫폼별 설정(Android 해시키, iOS URL 스킴)** 이 선행돼야 하고 그게 없으면 버튼을 눌러도 아무 일도 안 일어난다.
- **결정**: SDK 를 넣지 않는다. 소셜 버튼은 1.5초 지연 후 "신규 가입"으로 처리하고, 이메일은 `auth_screen.json` 의 `demoAccounts` 와 대조한다.
  - `parent@test.com` / `1234` — 기존 계정, **프로필 없음** → 프로필 등록 스텝
  - `parent2@test.com` / `1234` — 기존 계정, 프로필 있음 → 홈
- **이유**:
  - 목업에서 검증할 것은 OAuth 자체가 아니라 **로그인 이후의 세 갈래**(동의 → 프로필 → 홈)다. 특히 "로그인은 됐는데 프로필이 없는 계정"은 말로만 하면 다들 잊어버리는 경로라서, 눌러 볼 수 있게 만들어 두는 값이 크다.
  - 계정 3종을 코드에 박지 않고 더미에 둔 덕에, 시연 시나리오를 바꿀 때 코드를 안 건드린다.
- **주의**: ⚠️ `demoAccounts` 는 **목업 전용 필드**다. 실제 서버 응답에는 없고, 진짜 인증이 붙으면 `auth_screen.json` 의 해당 배열과 `AuthOptionsDto.demoAccounts` 가 함께 사라진다. `AuthOptions`(도메인 엔티티)에는 애초에 넣지 않았으므로 화면 코드는 이 필드를 모른다.
- **결과**: 교체 지점은 `AuthRepositoryMock` 하나다. 화면·ViewModel·라우터는 그대로 둔다.
