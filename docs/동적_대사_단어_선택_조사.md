# 조사: 동적 대사에서 단어 선택을 지원하려면

- 작성일: 2026-08-16
- 배경: 고정 대사 단어 담기(feat/dialogue-word-capture)를 구현하면서, LLM이
  만드는 동적 대사는 범위에서 뺐다. 이 문서는 동적 대사로 넓힐 때 무엇이
  필요한지 조사한 결과다.
- 결론 한 줄: **배관(API/프론트 구조)은 이미 동적 대사를 지원한다. 진짜
  선결 과제는 배관이 아니라 "쓰레기 단어가 단어장에 들어가는 것을 막는
  품질 게이트"이고, 이건 백엔드 소규모 작업이다.**
- 진행 상태(2026-08-16): **1단계(백엔드 유효성 게이트)와 2단계(프론트 게이트
  해제)를 구현했다.** 백엔드 422 INVALID_WORD(isRealWord 판정) + 프론트 동적
  대사 단어 선택 개방. 동적 대사에서는 예문을 보내지 않는다(오인식 인용
  가능성). 3단계(조사 분리)는 Nori 표제어 정규화로 함께 해결됐다 -
  `단어_저장_비용_속도_설계_조사.md` 참고.

## 1. 배관은 이미 되어 있다

동적 대사라고 해서 계약이 다르지 않다.

| 필요한 것 | 상태 |
|---|---|
| 저장 API | 있음. `POST /children/{childId}/words` 는 단어 출처를 가리지 않는다 |
| 장면 문맥 | 있음. 동적 대사도 지금 장면에서 나오므로 `sourceSceneId` 를 그대로 보낼 수 있다 |
| 예문 | 있음. 표시 중인 문장을 예문으로 보내는 로직이 동적 대사에도 그대로 적용된다 |
| 프론트 게이트 해제 | 한 줄. `play_view.dart` 의 `_fixedDialogue` 분기가 유일한 차단 지점이라, 이 조건만 풀면 동적 대사도 단어 단위로 눌린다 |

즉 "동적 대사 지원"을 코드만 보고 말하면 반나절 작업이다. 문제는 그 다음이다.

## 2. 진짜 문제: 원문 품질

동적 대사를 뺀 이유는 구현이 어려워서가 아니라 **단어장이 아이가 두고두고
다시 보는 학습 기록**이기 때문이다. 동적 대사에는 두 가지 오염 경로가 있다.

### 2-1. 아이 오인식 단어가 대사에 인용된다

캐릭터는 아이 발화를 되받는다("**방비**라고 했구나!"). 아이 발화는 STT를
거치므로 오인식 단어가 대사에 그대로 인용될 수 있고, 아이가 그 단어를
궁금해하며 누르면 **존재하지 않는 단어가 단어장에 저장된다.**

백엔드 #83(어휘 교정)이 병합되면 이야기 어휘 근접 오인식은 줄지만,
일반 어휘 오인식은 교정 대상이 아니라 경로가 남는다.

### 2-2. 서버 뜻 생성이 검증을 하지 않는다

실코드 확인 결과(`WordMeaningLlmClient.generate`), 뜻 생성이 실패하거나
단어가 엉터리여도 **"지금은 뜻을 알려줄 수 없어요"라는 대체 문구로 조용히
저장까지 간다.** 즉 지금 구조에서는 쓰레기 단어를 서버가 걸러 주지 않는다.

고정 대사는 원문이 검수된 글이라 이 구멍을 밟을 일이 없지만, 동적 대사를
열려면 이 구멍부터 막아야 한다.

## 3. 제안: 단계별 진행

### 1단계 - 백엔드 유효성 게이트 (동적 대사 지원의 선결 과제)

뜻 생성 LLM에게 "실제 쓰이는 한국어 낱말인가"를 함께 판정시킨다.

- `WordMeaningPromptBuilder` 출력 스키마에 `isRealWord`(boolean) 추가
- false 면 저장하지 않고 422 `INVALID_WORD` 응답 (ErrorCode 추가)
- 프론트는 "이 말은 단어장에 담기 어려워요. 다시 골라 볼까?" 안내

호출 흐름과 LLM 왕복 횟수는 그대로라 비용 증가가 없다. 이 게이트는
고정 대사에서도 안전망이 되므로 동적 확장과 무관하게 넣을 가치가 있다.

### 2단계 - 프론트 게이트 해제 + UI 다듬기

- `_fixedDialogue` 조건 완화 (동적 대사에도 `onWordTap` 전달)
- 대사가 다음 턴으로 교체되기 전, 확인 줄이 떠 있는 동안 턴이 진행되면
  확인 줄을 접는 처리(현재도 동적 전환 시 `_pendingWord` 를 비우는 코드가
  있어 소폭 보강이면 된다)

### 3단계 - 조사(助詞) 분리 (선택, 품질 개선)

> 후속 조사에서 별도 문서로 확장했다. 형태소 분석기 선정(KOMORAN이 아니라
> Nori 권장)과 LLM 비용/응답 속도 절감 4계층 설계는
> `단어_저장_비용_속도_설계_조사.md` 참고.

현재는 "기왓장이"를 누르면 조사째 저장된다. 형태소 분석 없이 끝 글자를
자르면 "마을"의 "을"처럼 낱말을 훼손해서 일부러 떼지 않았다.

제대로 하려면 서버(JVM)에 형태소 분석기를 붙인다.

- 후보: KOMORAN(아파치 2.0, 순수 자바, 의존성 가벼움), Open Korean Text(트위터
  출신, 스칼라/JVM)
- 저장 직전에 명사 원형을 추출해 `word` 를 정규화하고, 화면에는 아이가
  누른 그대로("기왓장이")를 보여 주되 단어장에는 "기왓장"으로 담는 방식
- 이 단계는 고정 대사 담기의 품질도 함께 올린다

### 진행 판단

| 단계 | 작업 위치 | 크기 | 없이 열면 |
|---|---|---|---|
| 1단계 게이트 | 백엔드 | 소 (프롬프트+에러코드) | 쓰레기 단어가 단어장에 쌓인다 |
| 2단계 해제 | 프론트 | 소 (조건 한 줄+보강) | - |
| 3단계 형태소 | 백엔드 | 중 (라이브러리 도입) | 조사째 저장(지금과 동일, 치명적이지 않음) |

**권장 순서: 1단계가 병합된 뒤 2단계를 연다.** 3단계는 별도 판단.

## 4. 참고: 이번 구현에서 동적 대사와 공유되는 것

- 단어 담기 통로(`DialogueWordCapture`)와 확인 줄 UI는 출처를 가리지 않게
  만들어 두었다. 동적 확장 시 재사용된다.
- 표시 중 문장을 예문으로 잡는 로직(`_pendingWordSentence`)도 그대로 쓴다.
- 단어장 화면 실서버 연동(#32)이 병합되면 담기 통로를 word 기능 계층으로
  합치는 후속이 남아 있다(`dialogue_word_capture.dart` 머리 주석).
