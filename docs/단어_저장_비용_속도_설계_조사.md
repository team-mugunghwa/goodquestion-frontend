# 조사: 단어 저장의 LLM 비용/응답 속도 최소화 설계

- 작성일: 2026-08-16
- 배경: 고정 대사 단어 담기(feat/dialogue-word-capture)가 저장 1건마다 서버
  뜻 생성 LLM을 1회 호출한다. 금전 비용과 응답 속도를 함께 줄이는 구조를
  조사했다. [[동적_대사_단어_선택_조사]]의 후속이다.
- 결론 한 줄: **형태소 분석기(표제어 정규화)를 맨 앞에 두고, 그 표제어를
  키로 "중복 -> 사전 -> 캐시 -> LLM" 4계층을 차례로 거르면, LLM 호출을
  "서비스 전체에서 단어당 최대 1회"로 줄이면서 대부분의 저장을 ms 단위로
  끝낼 수 있다. 분석기는 KOMORAN이 아니라 Nori(lucene-analysis-nori)를
  권장한다(3절).**

## 1. 지금 비용이 나가는 지점

현재 `WordbookService.create` 흐름 (백엔드 develop 기준):

```
중복 검사(문자열 완전 일치) -> 뜻/예문 없으면 LLM 생성 -> 저장
```

- 저장 1건 = LLM 1회. 아이가 단어를 담을 때마다 왕복 1~3초 + 토큰 비용.
- 중복 검사가 완전 일치라 "기왓장이"와 "기왓장을"은 딴 단어다. 같은 단어에
  LLM이 여러 번 나가고 단어장에도 여러 벌 쌓인다.
- 뜻 생성이 실패하면 "지금은 뜻을 알려줄 수 없어요"가 **영구 저장**된다.
  재생성 경로가 없다(실코드 확인: `WordMeaningLlmClient.FALLBACK`).

## 2. 절감 4계층 설계

모든 계층의 키는 **표제어**(조사를 뗀 원형)다. 그래서 형태소 분석기가
파이프라인의 맨 앞에 와야 하고, 이것이 LLM 표제어 방식 대신 분석기를
선택해야 하는 구조적 이유다(2-1).

```
아이가 "기왓장이" 담기
  |
  v
[0] 표제어 정규화 (형태소 분석기)          ms, 0원   "기왓장이" -> "기왓장"
  |
  v
[1] 아이 단어장 중복 검사 (표제어 기준)     ms, 0원   있으면 409 -> 끝
  |
  v
[2] 이야기 어휘 사전 조회 (뜻 포함, 신설)   ms, 0원   있으면 복사 저장 -> 끝
  |
  v
[3] 전역 생성 캐시 조회 (신설)             ms, 0원   있으면 복사 저장 -> 끝
  |
  v
[4] LLM 생성 + 캐시 적재                  1~3초     서비스 전체에서 단어당 1회
```

### 계층별 근거

**[1] 중복 차단이 LLM 호출 전에 와야 한다.** 이야기에는 같은 단어가 여러
장면에 반복해 나온다. 표제어 기준으로 저장 전에 걸러야 재담기가 0원이 된다.
LLM에게 표제어를 물어보는 구조라면 중복인지 알기 위해 먼저 돈을 써야 해서
이 계층이 성립하지 않는다.

**[2] 고정 대사의 어휘는 폐집합이다.** 이야기와 장면은 시드로 관리되므로
고정 대사에 나오는 낱말 전체를 미리 알 수 있다. 다만 **현재 DB에는 뜻이
없다** - `story_scenes.proper_nouns`(text[])는 STT 힌트용 단어 목록일 뿐이다
(데이터베이스_설계.md, 실스키마 확인). 따라서 "뜻을 포함한 이야기 어휘
사전"은 신설 테이블이다.

제안: `story_vocabulary(story_id, word(표제어), meaning, example_sentence)`.
시드 작성 시 한 번 채우면(오프라인에서 LLM으로 초안 생성 후 검수 가능)
고정 대사에서 담는 단어의 대부분이 이 계층에서 끝난다. **검수를 거친 뜻**이
들어가므로 품질도 LLM 즉석 생성보다 좋다.

**[3] 아이가 달라도 단어는 같다.** wordbook은 아이별 테이블이라 아이 A가
담아 생성된 뜻을 아이 B가 재사용할 방법이 지금은 없다. 전역 캐시
(`word_meaning_cache(word, story_id nullable, meaning, example_sentence)`)를
두면 같은 단어의 생성 비용이 서비스 전체에서 1회로 떨어진다.

주의 - **문맥 의존 뜻과의 긴장**: 단어-06 요건은 "같은 단어라도 이야기 안에서
쓰인 뜻"으로 풀이하는 것이다. 전역 캐시 키를 단어로만 잡으면 이야기 A의
뜻이 이야기 B에 재사용될 수 있다. 키를 `단어 + 이야기`로 잡으면 안전하고,
그래도 이야기당 1회로 줄어든다. 단어만 키로 쓸지는 팀 결정 사항.

**[4] 실패를 캐시에 넣지 않는다.** 1절의 "실패 뜻 영구 저장" 문제를 캐시가
증폭시키면 안 된다. LLM 실패 시 캐시에는 적재하지 않고, 저장된 단어의
뜻 재생성 경로(예: 단어장 조회 시 fallback 뜻이면 재시도)를 함께 두는 것을
권장한다.

### 응답 속도

- 계층 [1]~[3] 히트: DB 조회 1~2회 = **수십 ms**. 현재 1~3초 대비 체감이
  즉답으로 바뀐다. 고정 대사 담기는 [2] 적재 후 거의 전부 여기 떨어진다.
- 계층 [4]만 기존과 같은 1~3초. 비동기화(먼저 저장하고 뜻은 나중에 채움)로
  더 줄일 수 있으나 상태 관리가 복잡해져 이번 범위에서는 권장하지 않는다.

### 추가 고려사항 (열거)

- 형태소 분석 실패/미등재어: 원형을 못 찾으면 **누른 그대로 저장**으로
  후퇴한다. 지금 동작과 같으므로 더 나빠질 일이 없다.
- 화면 표시: 아이가 누른 형태("기왓장이")를 하이라이트에 그대로 보여 주되,
  담기 확인 문구와 저장은 표제어("기왓장")로. 프론트가 표제어를 미리 알
  방법이 없으므로 응답에 저장된 단어를 담아 안내 문구에 쓰면 된다.
- 기존 데이터: 이미 조사째 저장된 단어가 소수 있다. 마이그레이션은 건수가
  적어 수동 정리로 충분하다.
- STT 오인식 유래 단어(동적 대사 확장 시): [[동적_대사_단어_선택_조사]]의
  유효성 게이트와 이 파이프라인의 [4] 앞에 함께 둔다.

## 2-1. 트레이드오프: LLM 표제어 vs 형태소 분석기

| | LLM 표제어 (기존 호출에 필드 추가) | 형태소 분석기 |
|---|---|---|
| 호출당 비용 증가 | 출력 토큰 몇 개 (미미) | 0 |
| **중복 재담기** | 호출 후에야 중복 발견 - 절감 불가 | **호출 전 차단 - 0원** |
| **사전/캐시 계층** | 키(표제어)를 만들려면 호출 필요 - 계층 무력화 | **키를 0원에 생성 - 계층 성립** |
| 응답 속도 | 항상 LLM 왕복 포함 | 계층 히트 시 ms |
| 결정론/테스트 | 불가 | 가능 ("마을"이 "마"가 안 됨을 테스트로 고정) |
| 도입 부담 | 없음 | 라이브러리 1개 + 메모리 확인 |

호출당 토큰만 보면 차이가 없지만, **호출 횟수를 줄이는 2절의 계층 구조가
표제어를 0원에 만들 수 있어야 성립**하므로 형태소 분석기가 맞다.

## 3. 형태소 분석기 선정: KOMORAN이 베스트 프랙티스인가

결론부터: **아니다. 2026년 현재 JVM 한국어 형태소 분석의 베스트 프랙티스는
Nori(lucene-analysis-nori)다.** 유지보수 사실관계(2026-08-16 GitHub/Maven
Central API로 직접 확인)가 근거다.

| | Nori (lucene-analysis-nori) | KOMORAN | Open Korean Text |
|---|---|---|---|
| 개발 주체 | Apache Lucene 프로젝트 공식 모듈 | shineware (개인/소규모) | 커뮤니티 (트위터 출신) |
| 최신 릴리스 | **10.4.0, 2026-02** | **3.3.9, 2020-01 (6년 전)** | 저장소 마지막 푸시 2024-03 |
| 언어 | 순수 Java | 순수 Java | Scala (JVM) |
| 사전 | mecab-ko-dic (표준 사전) 내장, FST 압축 | 자체 사전 (Light/Full) | 자체 사전 |
| 메모리 | FST 기반이라 사전 대비 낮음 | Full 모델은 힙 수백 MB 가능 | 중간 |
| 라이선스 | Apache-2.0 | Apache-2.0 | Apache-2.0 |
| 실서비스 채택 | Elasticsearch/OpenSearch 한국어 분석 표준 | 튜토리얼/사내 도구 다수 | 소셜 텍스트 처리 |
| API 단순성 | Lucene Tokenizer 관용구 필요 (코드 약간 김) | 매우 단순 (`analyze()`) | 단순 |

### 왜 Nori인가

1. **유지보수가 살아 있다.** Lucene 릴리스 주기에 실려 몇 달 간격으로
   나온다(2026-02에 10.4.0). KOMORAN은 마지막 릴리스가 2020년으로, JDK가
   올라가거나 버그를 만나도 고쳐질 기대가 낮다. 우리는 JDK 25를 쓰므로
   구식 라이브러리 리스크가 실질적이다.
2. **사전이 표준이다.** mecab-ko-dic은 한국어 형태소 분석에서 가장 널리
   검증된 사전이고, Elasticsearch/OpenSearch의 한국어 분석이 전부 이 조합
   위에 있다. "베스트 프랙티스"라고 부를 근거가 여기 있다.
3. **의존성이 하나다.** `org.apache.lucene:lucene-analysis-nori` 하나로
   끝나고, FST로 압축된 사전이 jar에 내장이라 배포물 관리가 없다.
4. KOMORAN의 강점(API 단순, 사용자 사전 추가 용이)은 인정하나, 6년 무릴리스
   리스크를 상쇄할 정도는 아니다. 고전 어휘("곶감", "별주부" 등)가 사전에
   없으면 Nori도 사용자 사전(user dictionary)을 지원한다.

### 도입 전 검증 계획

1. 이야기 어휘 표본(기왓장, 장대, 며느리, 곶감, 별주부, 아궁이 등)을
   Nori로 분석해 명사 원형이 제대로 나오는지 확인. 안 나오는 낱말은
   사용자 사전에 추가.
2. "마을/사과/기왓장이/장대가" 부류로 과절단 회귀 테스트 작성.
3. Railway 컨테이너에서 힙 사용량 실측(기동 전후 비교) 기록.

## 4. 권장 진행 순서

1. 백엔드: Nori 도입 + 표제어 정규화 + 표제어 기준 중복 검사(계층 0, 1)
2. 백엔드: 이야기 어휘 사전 테이블 + 시드(계층 2) - 뜻 검수 포함이라 별도 PR
3. 백엔드: 전역 생성 캐시(계층 3) - 캐시 키(단어 vs 단어+이야기) 팀 결정 후
4. 프론트: 저장 응답의 표제어를 안내 문구에 반영

1번만으로도 "재담기 0원 + 과절단 방지"가 확보되고, 2번이 들어오면 고정
대사 담기의 LLM 비용이 사실상 0으로 떨어진다.
